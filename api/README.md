# api

The Online Judge backend: one Python 3.13 service (Flask 3 + gunicorn, SQLAlchemy Core + psycopg 3 on
PostgreSQL, pika on RabbitMQ). It replaces the former `rest` (Go HTTP edge), `midlayer` (business logic)
and `dao` (persistence) services and keeps their HTTP contract, database schema and RabbitMQ topology.

One image, two processes:

* **api** (default `CMD`): applies pending migrations, then serves `/api/v1` with gunicorn.
* **worker** (`python -m app.worker`): consumes `judge.events` (runner results → verdicts) and
  `judge.jobs.dead` (→ `FAILED`), and re-publishes stale open submissions at startup.

```
webapp ─proto JSON─> api ─SQL─> postgres
                      │ AMQP: judge.jobs (ExecuteJob), judge.rpc.<uuid> (custom-run replies)
                      v
                   rabbitmq ── judge.jobs ──> runner × N
                      │   <── judge.events ──┘
                      v
                   worker ─SQL─> postgres
```

The contract lives in `../proto` (`judge.proto`: HTTP messages, `types.proto`, `runner.proto`: RabbitMQ
messages and topology). `app/gen/` is generated by `make gen` at the repo root; never edit it.

## Layers

Dependencies point downward only (rules in [AGENTS.md](AGENTS.md)).

| Path | Role |
|---|---|
| `app/controllers/` | HTTP only: `public_controller.py`, `admin_controller.py` (parse a proto request, call ONE service method, `proto_response`); `http.py` (proto JSON, path/query params, request id, CORS, body limits, admin auth, rate limit, `app.errors` → `ErrorResponse`); `rate_limit.py`; `consumers.py` (the worker's AMQP "controllers": decode → one service call → ack/requeue) |
| `app/services/` | Business logic on proto messages: `validation`, `judging` (output normalisation, verdict precedence), problems, submissions (submit, judging pipeline, recovery), runs, status, languages. No Flask, SQL or pika |
| `app/repositories/` | All I/O: `Database` (engine, error translation, migrations), `ProblemRepository`, `SubmissionRepository`, `codecs` (enum ⇄ stored strings, results JSONB), `JobQueue` (topology, publisher confirms, RPC, queue stats, consumer loop) |
| `app/__init__.py` | `create_app(settings, repositories)`: wiring (tests inject fakes) + `flask migrate` command |
| `app/worker.py` | `python -m app.worker` / `python -m app.worker healthcheck` |
| `app/healthcheck.py` | Docker `HEALTHCHECK` of the api (`GET /healthz`) |
| `migrations/` | SQL migrations, copied verbatim from dao (schema unchanged) |
| `wsgi.py`, `gunicorn.conf.py` | gunicorn entry point and settings |

## HTTP API (`/api/v1`, canonical proto JSON)

Bodies and responses are the `*Request` / `*Response` messages of `proto/oj/v1/judge.proto`: camelCase
(snake_case also accepted in bodies), enums by name, int64 as strings, Timestamps as RFC 3339, every
field with a default value emitted. Unknown fields or bad JSON → 400; an empty body is `{}`; path
parameters (positive integers, else 400) override body fields.

| Method | Path | Request → Response | Success |
|---|---|---|---|
| GET | `/healthz` | liveness, no dependencies → `{"status":"ok"}` | 200 |
| GET | `/api/v1/status` | `GetStatusRequest` → `GetStatusResponse` | 200 |
| GET | `/api/v1/languages` | `ListLanguagesRequest` → `ListLanguagesResponse` | 200 |
| GET | `/api/v1/problems` | `ListProblemSummariesRequest` → `ListProblemSummariesResponse` | 200 |
| GET | `/api/v1/problems/{id}` | `GetProblemDetailRequest` → `GetProblemDetailResponse` | 200 |
| POST | `/api/v1/submissions` *(rate limited, 512 KiB)* | `SubmitRequest` → `SubmitResponse` | 202 |
| GET | `/api/v1/submissions?problemId=&username=&limit=&offset=` | `ListSubmissionSummariesRequest` → `…Response` | 200 |
| GET | `/api/v1/submissions/{id}` | `GetSubmissionDetailRequest` → `GetSubmissionDetailResponse` | 200 |
| POST | `/api/v1/run` *(rate limited, 2 MiB)* | `RunCodeRequest` → `RunCodeResponse` | 200 |
| GET | `/api/v1/admin/verify` | → `{"admin": true}` | 200 |
| POST | `/api/v1/admin/problems` | `AddProblemRequest` → `AddProblemResponse` | 201 |
| PUT | `/api/v1/admin/problems/{id}` | `EditProblemRequest` → `EditProblemResponse` | 200 |
| DELETE | `/api/v1/admin/problems/{id}` | `RemoveProblemRequest` → *(no body)* | 204 |
| GET | `/api/v1/admin/problems/{problemId}/testcases` | `ListProblemTestCasesRequest` → `…Response` | 200 |
| POST | `/api/v1/admin/problems/{problemId}/testcases` | `AddTestCaseRequest` → `AddTestCaseResponse` | 201 |
| DELETE | `/api/v1/admin/problems/{problemId}/testcases/{id}` | `RemoveTestCaseRequest` → *(no body)* | 204 |

`problem_id` is accepted as an alias of `problemId` in the submissions query. Admin routes need
`Authorization: Bearer $ADMIN_TOKEN` (constant-time compare; bodies up to 64 MiB); they answer 403 when
`ADMIN_TOKEN` is empty.

Every non-2xx body is an `oj.v1.ErrorResponse` (`{"error": "...", "details": []}`):

| Cause | HTTP | `error` |
|---|---|---|
| bad JSON / unknown field / invalid path or query parameter | 400 | describes it (`details` has the parser message) |
| missing or wrong admin token / admin disabled | 401 (`WWW-Authenticate`) / 403 | fixed message |
| unknown route / wrong method | 404 / 405 | `not found` / `method not allowed` |
| body over the route limit | 413 | `request body too large` |
| `ValidationError` | 422 | names the field |
| `NotFound` | 404 | message |
| `Conflict` (duplicate slug) | 409 | message |
| rate limit (`Retry-After`) / `QueueFull` | 429 | `rate limit exceeded, retry in Ns` / message |
| `Unavailable` (Postgres or RabbitMQ down, runner failed a run) | 503 | `service unavailable` (details logged) |
| `Timeout` (no runner answered a custom run within `RUN_TIMEOUT_S`) | 504 | message |
| anything else | 500 | `internal error` (logged) |

Every response carries `X-Request-ID` (the client's if it matches `[A-Za-z0-9_-]{1,64}`, else generated);
gunicorn's access log (stdout, without `/healthz`) includes it. CORS follows `CORS_ORIGINS`.

## Message flow

Topology and AMQP properties follow the header of `proto/oj/v1/runner.proto`. Both processes declare the
quorum queues with identical arguments when they connect (`judge.jobs`: `x-delivery-limit=3`,
dead-lettered to `judge.jobs.dead`).

```
POST /submissions ─> validate ─> queue depth >= MAX_QUEUE_DEPTH? 429 ─> INSERT PENDING ─> publish ExecuteJob
                     job_id "submission-<id>", correlation_id = job_id, reply_to = judge.events,
                     persistent, mandatory, publisher confirm. Publish fails -> FAILED/INTERNAL_ERROR + 503.
                     A problem without test cases -> FAILED immediately.

runner ─> judge.events ─> worker: started  -> JUDGING        if status in [PENDING]
                                  finished -> judge -> FINISHED + verdict if status in [PENDING, JUDGING]
                                              REJECTED / INTERNAL_ERROR -> FAILED / INTERNAL_ERROR
          The status check is an atomic compare-and-set in the UPDATE; a lost CAS (late or duplicate event)
          is ignored. Acked after the write; database unavailable -> nack(requeue) after 2 s
          (on RabbitMQ 4 quorum queues nack(requeue=true) does not raise x-delivery-count, so events are
          never dropped during an outage; a handler bug -> reject without requeue).

judge.jobs.dead ─> worker: submission jobs -> FAILED / INTERNAL_ERROR (same CAS); custom runs: ack.

POST /run ─> publish ExecuteJob (UUID job_id, reply_to = this thread's exclusive judge.rpc.<uuid> queue,
             AMQP expiration = RUN_TIMEOUT_S) and wait for `finished` (process_data_events) -> 504 on timeout.
```

Worker startup recovery: submissions in PENDING/JUDGING not updated for `RECOVER_AFTER_S` are
re-published (duplicates are harmless thanks to the compare-and-set); failure is logged, not fatal.

pika's `BlockingConnection` is not thread-safe, so each api thread owns a connection + confirm channel +
reply queue (created lazily, without AMQP heartbeats, re-created and retried once after a broker error).

Judging rules: outputs are compared after normalisation (CRLF/CR = LF, trailing whitespace of each line
and trailing blank lines ignored; leading whitespace and inner blank lines significant). The verdict is
the verdict of the first failing test, else ACCEPTED. Hidden tests never leave the api (problem detail
only exposes samples); submission lists omit source, message and per-test results.

## Database

`flask --app wsgi migrate` (run by the container before gunicorn) applies `migrations/*.sql` not yet in
`schema_migrations(version TEXT PRIMARY KEY, applied_at)`, each in a transaction, under Postgres advisory
lock `727001` — the same table, versions and lock as dao, so a database dao already migrated is
recognised and left untouched, and concurrent starts are safe. Enums are stored as before: language
`python|c|cpp|javascript`, difficulty `easy|medium|hard`, status `PENDING|JUDGING|FINISHED|FAILED`, verdict
`''|AC|WA|TLE|MLE|OLE|RE|CE|IE`; `submissions.results` rows are
`{"test":1,"verdict":"AC","time_ms":12,"memory_kb":9000,"sample":true}` (unparseable legacy rows read as
empty).

## Configuration

| Variable | Default | Description |
|---|---|---|
| `PORT` | `8000` | HTTP port (api) |
| `DATABASE_URL` | `postgresql+psycopg://oj:oj@localhost:5432/oj` | Postgres DSN (`postgres://` also accepted) |
| `RABBITMQ_URL` | `amqp://guest:guest@localhost:5672/` | Broker URL |
| `ADMIN_TOKEN` | *(empty → admin API off)* | Bearer token for admin routes (≥ 16 random characters) |
| `CORS_ORIGINS` | `*` | Comma-separated allowed origins |
| `RATE_LIMIT_PER_MIN` / `RATE_LIMIT_BURST` | `20` / `5` | Token bucket per client for POST submissions + run |
| `TRUST_PROXY_HEADERS` | `false` | Client IP from `X-Real-IP` / `X-Forwarded-For` (only behind a trusted proxy) |
| `RUN_TIMEOUT_S` | `30` | Custom-run wait (and the job's AMQP expiration) |
| `MAX_QUEUE_DEPTH` | `1000` | Submit answers 429 at this `judge.jobs` depth |
| `RECOVER_AFTER_S` | `300` | Age after which the worker re-publishes open submissions at startup |
| `API_THREADS` | `16` | gunicorn threads (and DB pool size) |
| `WORKER_HEALTH_FILE` | `/tmp/worker-healthy` | Touched every second while the worker consumes |
| `JOBS_QUEUE`, `DEAD_QUEUE`, `EVENTS_QUEUE`, `REPLY_QUEUE_PREFIX` | runner.proto names | Tests only |

**One gunicorn worker process, `API_THREADS` threads (`gthread`)**: the rate limiter is in process
memory, so a single process keeps it exact. Scale with threads; several processes or replicas would
each enforce their own limit.

RabbitMQ permissions for the api/worker user: configure `^judge\..*$`, write `^amq\.default$`,
read `^judge\..*$`. The image runs as uid/gid 10001 and works with a read-only root filesystem plus a
tmpfs on `/tmp` (gunicorn worker heartbeat, worker health file).

## Development

```bash
uv venv --python 3.13 .venv && uv pip install --python .venv -r requirements-dev.txt
.venv/bin/ruff check . && .venv/bin/ruff format --check .
.venv/bin/pytest                                    # unit + functional (Postgres/RabbitMQ tests skip)

# against real services (throwaway containers)
docker run -d --name oj-test-postgres -p 127.0.0.1:55432:5432 \
  -e POSTGRES_USER=oj -e POSTGRES_PASSWORD=oj -e POSTGRES_DB=oj_test postgres:17-alpine
make -C .. test-broker                              # RabbitMQ on 127.0.0.1:5673
TEST_DATABASE_URL=postgresql+psycopg://oj:oj@127.0.0.1:55432/oj_test \
RABBITMQ_TEST_URL=amqp://oj:oj@127.0.0.1:5673/ .venv/bin/pytest

DATABASE_URL=... RABBITMQ_URL=... .venv/bin/flask --app wsgi migrate
DATABASE_URL=... RABBITMQ_URL=... .venv/bin/gunicorn -c gunicorn.conf.py wsgi:app
DATABASE_URL=... RABBITMQ_URL=... .venv/bin/python -m app.worker
docker build -t online-judge/api:latest .
```
